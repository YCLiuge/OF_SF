# 客户端构建对照

这四份 Windows 发行包都使用 Unity IL2CPP。开服客户端保留了早期版本的资源目录，可用来核对资源命名和版本演变。检查四份游戏目录时，均未找到 Unity 编辑器工程的 `Assets`、`ProjectSettings/ProjectVersion.txt`、`Packages/manifest.json` 组合，也未找到 C# 源文件、工程文件、独立的 `Managed/Assembly-CSharp.dll` 或面向玩家的模组开发接口。渠道登录 SDK、引擎运行库和脚本程序集名称均有各自的运行用途。

## 实物记录

| 发行包 | UnityFS 声明的引擎 | 发行基础版本 → 活动资源版本 | 基础包数 → 活动包数 | 声明的程序集数 |
| --- | --- | --- | --- | ---: |
| 开服 PC | 2021.3.45f1c1 | 2025-03-21-17-15-05 → 2025-04-06-19-22-03 | 5,218 → 5,234 | 170 |
| TapTap 国服 | 2021.3.45f2c1 | 2026-10-21-14-05-50 → 2026-11-25-19-54-41 | 8,917 → 8,936 | 177 |
| B站国服 | 2021.3.45f2c1 | 2026-10-21-14-06-13 → 2026-11-25-19-54-31 | 8,917 → 8,936 | 168 |
| Steam 国际服 | 2021.3.45f2c1 | 2026-10-24-12-00-58 → 2026-11-25-17-28-12 | 9,809 → 9,814 | 169 |

开服的游戏本体位于下载器里的 `Data/download/games/11113/install`。Steam 安装目录在本次检查时只有基础清单；表中热更来自另一份本机保存的国际版资源缓存，已逐字节核对两者的基础清单摘要。三个现行渠道的 IL2CPP 元数据头版本均为 31。旧版头的版本字段无法按同一格式识别。

在所列活动清单中，开服 PC 与 TapTap 共有 5,086 个同名资源包，全部摘要不同。TapTap 与 B 站同名同摘要的有 8,803 个，另有 133 个同名包内容不同。Steam 与 TapTap 同名同摘要的有 7,824 个，另有 925 个同名包内容不同。这里按清单的逻辑包名与压缩包摘要比较。

四套程序集清单均列有 `IFix.Core.dll` 和 `YooAsset.dll`。四份基础资源清单均未索引独立的代码补丁。四份活动清单都索引了 `Assets/ResBundle/CodePatch/Standalone/Assembly-CSharp.patch.bytes`。本机三份现行渠道的补丁容器分别与其自己的清单相符，三者的摘要互不相同。开服样本的容器长度为 108,514 字节，实际 MD5 为 `47edb7f34797097239500e48c3996a32`，清单记录为 `d4bce3bf2eb69eceea7533cf2ab7daa4`。目前无法确定差异原因。运行库名称和补丁条目可以证明发行物包含相应内容，无法证明某次启动实际执行了其中哪段代码。

## 在其他安装目录复查

在源码仓库根目录使用 Python 3.11 或更新版。工具读取 UnityFS 头、程序集清单和 YooAsset 的版本指针，只对索引到的代码资源容器读取内容并核对 MD5。它对游戏文件只读，生成的 JSON 包含样本标记、版本、计数与摘要。

```powershell
py -3 tools/inspect_client_build.py --client old "D:\旧下载器" --client cn "D:\国服游戏目录" > builds.json
py -3 tools/inspect_client_build.py --client steam "D:\国际服游戏目录" --cache steam "D:\已保存的国际服资源目录"
py -3 tools/test_inspect_client_build.py
```

`effective_bundle_diff` 以第一个样本为基准。未提供活动缓存时，用该样本的基础清单。`--cache` 指定的目录须有 `launcher_Data`，并包含与该游戏相同的基础清单。只要清单本身无法校验，命令就以非零状态结束。清单可读时，`indexed_code_assets` 中的 `verified_local` 记录通过内容校验的来源；为 `null` 时，可查 `mismatches` 区分缺文件、长度不符和摘要不符。容器校验结果随 JSON 输出，便于调用方决定是否采用这份样本。

## 在 Unity 编辑器中对照

仓库提供独立的编辑器包 [OF_SF 构建对照](../../unity/com.ofsf.build-review/README.md)。从 Package Manager 的 **+ → Add package from disk…** 选择 `unity/com.ofsf.build-review/package.json`，或用 **Add package from tarball…** 选择发布的 `.tgz`。打开 **Tools → OF_SF → 客户端构建对照**，载入上一步的 `builds.json`，即可并排查看参考样本和所选渠道的版本、资源数量与补丁校验。可复制校验摘要，也可切换样本或重新载入报告。

源码中的 `BuildReport.Load` 用于读取报告，`BuildCompareWindow` 负责窗口呈现，两者均可继续开发。包以 Unity 2021.3 为最低目标。本次使用已安装的 Unity 2022.3.55f1c1 程序集编译，并通过该版本的 Mono 验证了四份真实样本。该机缺少有效 Editor 许可证，批处理在打开工程前终止，菜单点击与窗口画面尚待在已激活的编辑器中验证。

## 从可维护的代码开始

为 OF_SF 开发自己的工具，可以直接读源码中提供的管理接口契约。下面的示例从本地代码列出只读操作及其参数，不要求安装游戏、登陆玩家账号或启动服务。

```python
import json
import subprocess
import sys

result = subprocess.run(
    [sys.executable, "-B", "OverField-Server/of.py", "admin", "schema"],
    check=True, capture_output=True,
)
operations = json.loads(result.stdout)["result"]["operations"]
for name, spec in sorted(operations.items()):
    if spec["readOnly"]:
        print(name, sorted(spec["inputSchema"].get("properties", {})))
```

要开发版本检查器，可直接消费上述 `builds.json`；要开发服主管理工具，可在自己的测试实例接入 `/admin/v1/openapi.json`。新增玩法可以由服务端独立实现并用原生消息回归测试。如需要在编辑器中修改原版场景、角色脚本和构建管线，还需另有对应的 Unity 源工程及依赖。[本机管理接口](本机管理接口.md)
