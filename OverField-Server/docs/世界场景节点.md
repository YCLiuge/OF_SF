# 同一世界的场景节点

每个节点运行一份 OF_SF 和自己的角色库。场景表 `scenes` 给每个参与分片的原生场景分配一个负责人。节点用独立端口直接连接负责人，互验 TLS 证书、世界标识和场景表摘要。玩家仍通过原来的玩家网关进入自己的区服。部署不需要注册中心。

## 配置两台机器

每个节点生成一份自己的证书和私钥。将下面的 DNS 名换成其他节点连接此机所用的名称。使用 IP 地址时，将 `DNS:` 换为 `IP:`。Windows 上的 OpenSSL 若缺少默认配置文件，可用 `-config` 指向现有的 openssl.cnf。

```sh
openssl req -x509 -newkey rsa:3072 -nodes -sha256 -days 365 -subj /CN=west -addext "subjectAltName=DNS:west.example" -addext "basicConstraints=critical,CA:FALSE" -addext "keyUsage=critical,digitalSignature,keyEncipherment" -addext "extendedKeyUsage=serverAuth,clientAuth" -keyout west.key -out west.pem
openssl x509 -in west.pem -noout -fingerprint -sha256
```

双方交换公开的 `.pem` 并用独立渠道核对 SHA-256。私钥只放在对应的机器上，文件权限只授予区服服务账户。每个节点可以使用自己的证书颁发机构或自签证书。节点清单填写各自实际使用的**叶证书**。

下面是 west 节点的 `world.json`。示例场景和角色 ID 区间需要替换为本服实际值。east 节点将 `node` 改为 `east`、`key` 改为 `east.key`。两个节点均需本机可以到达的对端地址，并在防火墙上允许对端连接场景端口。

```json
{
  "world": "sakura",
  "node": "west",
  "bind": "0.0.0.0",
  "key": "west.key",
  "nodes": {
    "west": {"host":"west.example","port":19441,"cert":"west.pem","uids":[100000000,199999999]},
    "east": {"host":"east.example","port":19441,"cert":"east.pem","uids":[200000000,299999999]}
  },
  "scenes": {"101":"west","102":"east"}
}
```

1. 在每台机器运行 `python of.py federation-check --config world.json`。检查世界清单摘要一致、所属场景正确、各服的角色 ID 范围互不重叠；范围要覆盖本服参与跨节点场景的原生角色标识。
2. 让每台游戏进程的 `OF_FEDERATION_CONFIG` 环境变量指向自己的配置文件绝对路径，按原有方式启动区服。未设置该变量的区服按单机方式运行。
3. 在两台机器运行 `python of.py federation-check --config world.json --peers`。输出中每个 peer 的 `checks` 应为 `ok`；任一失败时退出码为 1。测试会使用本节点身份完成真实握手和往返。
4. 用不同节点的隔离角色进入同一已配置场景，核对进场、位置更新和离场，再进入由另一节点负责的场景。

## 运行边界

每个世界可配置 1–32 个节点和至多 4,096 个场景。节点身份、证书、UID 区间和场景归属共同确定清单版本。网络地址可以按机房分别设置。消息采用带长度的 UTF-8 JSON，单帧至多 256 KiB。同一对节点可以复用至多四个并行出站连接，每次读取有绝对截止时间。连接中断后调用方获得失败，传输层不会自动重放可能已生效的操作。

没有场景所有者的响应时，静态归属仍然有效。更换场景负责人、UID 区间、成员或证书时，应先让参与场景离场并停止相关节点，再同步新配置、重启和核对连通性。当前版本不包含运行中转移场景或选举新的负责节点。账号、密码、背包与经济写入继续由原服维护。
