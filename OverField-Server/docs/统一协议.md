# 《开放空间》原生基线与可选 Mod 协议

OF_SF 负责原版客户端的登录、角色存档、物品、经济和场景。overfiled-mod 可以在原有宿主中加载内容目录模块，读取同一区服发布的指南、打开本机已有的小游戏。两条路径可以独立启用。服主仍可运行 Lolo 的原有沙盒，选择原有沙盒时由 Lolo 管理该沙盒的进度。OF_SF 的掉率等社区规则见[上游对照](上游对照.md)。

| 调用方 | 接口与状态归属 | 本次验证边界 |
| --- | --- | --- |
| 原版 PC 客户端 | 原生 TCP / Protobuf。账号、档案、背包、抽卡、邮件由 OF_SF 既有处理器写入。 | 三个现行 Windows 安装的 733 个消息编号，以及 606 种请求和响应的顶层字段名和编号已核对。开服包仅核对构建清单和元数据指纹。 |
| Mod 玩家 | 独立 HTTPS 读取能力和内容。客户端负责展示指南和选择本地注册入口。 | 共用真实 TLS 网关、UTF-8 和 SHA-256。中国象棋和你画我猜沿用相应本地模块与原中继。游戏内画面待玩家手测。 |
| 服主 | `of.py content` 校验和原子发布目录。区服设置、发信、维护继续使用本地管理 API。 | 玩家凭证、服主令牌和玩家个人数据均不属于目录字段。 |
| Lolo、家园编辑、本地家园、聊天及其他 Mod 模块 | 沿用原实现及各自的存储和生命周期。 | 安装或移除目录模块独立于选择游戏后端。OF_SF 与 Lolo 各自管理自己的存档。 |

协议参考 OF-Contracts v0.1.0 候选设计，取用其原生档案、能力声明、内容版本和权威归属。已部署子集具有独立标识 `ofsf.extensions.v1`。支持范围由实际响应声明。候选中的 33 个 RPC、跨服和远程经济写入仍是独立设计范围。[原生档案与核验工具](https://github.com/YCLiuge/OF_SF/blob/main/contracts/v1/native-profile.json) · [原生玩法覆盖](客户端请求对照.md) · [Mod 固定基线](https://github.com/jianx14/overfiled-mod/tree/d97ad47648f4ac1d6cbd28b225ebdb30a8b3d089)

## 两次读取完成协商

1. 玩家选定区服根地址。读取 `GET /of-contracts/v1/realm`，核对标识、版本、玩家端档案和 `content.catalog.v1` 能力。`ruleset_revision` 为 `null` 表示当前区服未发布不可变的玩法规则版本。
2. 读取同一地址的 `GET /of-contracts/v1/content`。对收到的完整 UTF-8 正文字节计算 SHA-256，与 `content_manifest` 比对。重新排版、键排序或再次序列化都会改变摘要。
3. 内容版本须与第一份响应完全相同。读取方接受 `0.1.x`。服主在两次读取间发布时，摘要可能不同，读取方最多重新协商一次。校验通过后展示整份目录。
4. 旧区服、暂时不可达、未知能力或未知内容不会改变原游戏的登录与处理器。新接口仅返回公开数据。公网使用 HTTPS，本机调试可使用环回 HTTP；私有 CA 按区服指定，由客户端校验证书链和主机名。

这里的内容摘要只标识**当前发布的扩展目录**。客户端安装包和国服道具表有独立的来源和摘要。两个接口的字段、响应和文件格式见 [OpenAPI](contracts/openapi.json) 和[目录 JSON Schema](contracts/catalog.schema.json)。

## 发布与回退

从服务端发行目录运行下列命令。将 `PATH_TO_STATE` 换成正在运行区服的状态目录。Windows 免安装包可将 `python` 换成 `.\runtime-win64\python.exe`。

```sh
python of.py content validate docs/contracts/of-contracts-content.example.json
python of.py --state PATH_TO_STATE content publish docs/contracts/of-contracts-content.example.json
```

`validate` 只打印条目数与正文摘要。`publish` 用同目录临时文件完成原子替换，下次请求生效。默认目录为空。回退时重新发布前一份通过验证的 JSON；停用全部扩展入口时发布 `{"contract_version":"0.1.0","items":[]}`。旧玩家仍可用原有快捷键。若手工写入非法文件，目录接口返回 503，修复文件即可恢复。

[示例目录](contracts/of-contracts-content.example.json) 包含三种用法。服主可直接添加纯文字指南，也可以把不同标题的菜单项指向同一个已安装动作。条目顺序即显示顺序。`id` 在整个目录内唯一。`entry` 指向本地注册键。两者均用点分隔的小写命名空间，例如 `jianx14.chess`。文件不超过 64 KiB，每个目录至多 128 项，标题至多 80 个 Unicode 标量，指南正文至多 2,048 个并支持换行。

## 玩家使用 Mod

在已有 overfiled-mod 的独立游戏副本安装 `OfContractsModule`，指向运行本版 OF_SF 的玩家网关。游戏后端由当前登陆器或部署选择；更换内容目录地址只更换目录来源。使用 Lolo 的旧部署可以继续游玩其沙盒。安装器的 `-ModsDirectory` 参数指向已有宿主的 Mods 目录，玩家免编译。模块源码和安装说明已固定在[适配补丁](https://github.com/YCLiuge/OF_SF/blob/main/contracts/v1/adapters/overfiled-mod-of-contracts-v1.patch)。

维护者可在上游提交 `d97ad476` 的干净工作树中先运行 `git apply --check <补丁路径>`，再运行 `git apply <补丁路径>`，即可得到同一份模块源码。

玩家可在 `%LOCALAPPDATA%/OF_SF/mod-catalog.json` 中写入 `{"origin":"https://realm.example:18443"}`，按需添加 `ca` 指向服主给的 PEM。进入角色后按 **Alt+9**，输入 `ofcatalog` 查看目录，`ofcatalog open ofsf.fishing` 阅读示例，`ofcatalog refresh` 读取新版。原有 F9 象棋、F8 画板仍可独立使用；多人玩法沿用原宿主的聊天中继配置。

新增独立小游戏时，为本地 `ILogic` 模块实现 `IServiceProvider`。其 `GetService(typeof(IReadOnlyDictionary<string, Action>))` 返回愿意公开的本地动作表，例如 `lobby` 对应打开拼图面板。目录项可以写成：

```json
{"id":"games.puzzle","kind":"minigame","title":"拼图","entry":"module.puzzle.lobby"}
```

`puzzle` 必须匹配已安装模块 ID。玩家点击时目录模块重新从宿主查询当前实例和动作，因而可识别卸载、重新加载和缺失的动作。服主可添加这样的项目而无需重新构建 OF_SF 或目录模块。

## 二次开发时的边界

| 新内容 | 开发路径 | 写入权威 |
| --- | --- | --- |
| 攻略、玩法说明 | 添加 `guide` 条目，校验并热发布。 | 区服目录文件 |
| 新 Mod 小游戏 | 已安装模块注册本地动作，再由目录的 `minigame.entry` 引用。服主发布一个名字不会下载安装代码。 | 模块和原中继管理本局状态 |
| 新原生玩法、消耗或奖励 | 在 OF_SF 的既有领域处理器校验、持久化并回传原生响应。原生注册表和客户端资源决定原版玩家可以看到的表现。 | 当前区服的角色或场景处理器 |
| 以后由 Mod 发起的持久业务 | 增加独立、带版本的类型化能力，并在同一权威处理器内完成原生和 Mod 的校验与写入。目录协议只读。 | 该能力声明的服务端写入者 |

新增持久业务接口时，身份和会话代际由已认证的区服提供。一次业务意图使用稳定的操作 ID，重试先查持久收据并比较意图，再对首次执行检查版本和资格。资产、业务版本、收据和待发布事件在同一事务提交，随后发送回执。原生 `packet_id` 仅在其已验证的会话范围解释。相同内容的两次抽卡可以是两次合法操作。

场景扩展须标明房间、成员及其代际。只有已识别的纯移动数据可合并，交互事件要保持顺序。重连恢复需要房间快照和同一边界后的增量。新能力经过跨实现验证后再公布能力名。当前普通玩家目录向区服发送两次只读请求，无需启动附加数据库或 RPC 进程。


## 公共业务接口的演进顺序

下表区分现有原生操作和将来可以对扩展开放的类型化接口名。只有在 `DescribeRealm` 的能力清单中声明、且有对应权限与行为测试的接口，扩展才能调用。当前公开 HTTP 提供 `DescribeRealm` 与 `GetContentCatalog`。

| 领域 | 原生兼容边界 | 后续公共接口与验收条件 |
| --- | --- | --- |
| 会话、角色和背包 | 区服验证登录票据、处理档案与背包。 | `GetProfile`、`GetInventory` 使用已认证会话，身份来自服务端，按同一背包版本分页。换连接后拒绝旧会话写入。 |
| 购买、招募、领奖 | 原版继续发送已有编号，例如招募 1445/1446、邮件操作 1125/1126。 | `Purchase`、`DrawGacha`、`ClaimReward` 只接受业务意图，价格、概率、资格由服主的规则与内容版本决定。`GetOperation` 用于掉线后找回已提交结果。 |
| 房间与聊天 | 区分 OF_SF 原生场景与 Mod 中继房间。位置记录 1203 不能一概按普通请求生成同步回复。 | `JoinScene`、`SubmitInteraction`、`Subscribe` 使用房间和成员代际，换房及重新连接需覆盖离场、重放、静止实体位置与可靠事件。 |
| 管理与可选跨服 | 本机管理 API 和 Lolo 各自保留原管理入口。 | 管理写入由经过授权的同一业务处理器处理。跨服社交访问另协商节点身份、原服角色标识和可撤销租约，各服分别保管资产。 |

本版不占用原版消息编号。原生协议新增映射前，登记客户端档案、字段号与枚举、明确的回包及通知，再做隔离角色回归。不兼容的扩展消息变更使用新版本与能力名，旧的原生和 Mod 入口各按原生命周期运行。
