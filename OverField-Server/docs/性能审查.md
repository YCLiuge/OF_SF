基线为服务端 `ad981c6`。以下为 Windows x64 同机测试。查询耗时不含公网延迟，坐标耗时只计持久化路径。

| 实测工作量 | 基线 → 当前 | 验证内容 |
| --- | --- | --- |

| 24 名角色，57,600 次移动 | 存档向量编码 115,200 → 3,840 次；持久化用时中位数 113.56 → 74.75 ms | 两版均写入 1,920 行。另测两频道的 320 次移动、640 次投递，角色位置与广播一致；写入失败可重试。 |

从仓库根目录使用 [昵称基准](../../tools/benchmark_nickname_lookup.py)、[发布查询基准](../../tools/benchmark_release_queries.py) 和[坐标基准](../../tools/benchmark_pose_checkpoints.py)。用 `--help` 查看数据规模、服务端路径与轮数。发布查询使用相同测试工具分别量旧版和新版，读量统计在应用层。

### 旧档与外键

旧版成就表曾将成就编号同时指向玩家编号。本版首次打开旧库时，在同一事务内重建成就表，只保留其所属玩家关系。保留原有成就内容、行号、索引和触发器；异常会回滚。游戏主写连接启用 SQLite 外键检查。迁移遇到原有孤儿记录会保留，可在离线备份副本上运行 `PRAGMA foreign_key_check;` 检查。本机和公网的备份副本分别含 11,882 和 225,758 条成就。两次演练均逐条核对摘要，迁移后外键检查均无异常。

### 架构取舍

社区项目按频道维护成员，使用有界发送队列，并固定 Lolo 服务端与资源版本。OF_SF 已有频道索引和有界发送队列。本次根据本服回归保留广播语义，优化了存档时的编码。原版 Unity 客户端继续适用，道具、扣费和领奖仍在玩法事务内提交。[社区频道实现](https://github.com/jianx14/overfiled-mod/blob/cfdb9ed0b924f49f5f6d91f7dc23dbadfbc35ce5/%E6%9C%8D%E5%8A%A1%E5%99%A8/Chat.Server/ChannelRoom.cs) · [社区部署说明](https://github.com/jianx14/overfiled-mod/blob/cfdb9ed0b924f49f5f6d91f7dc23dbadfbc35ce5/private-server/SETUP.md)

本轮保留 SQLite WAL 单服写入和 PostgreSQL 报表副本。现有测量支持优化锁内工作量，跨库崩溃对账、高密度同场广播与持续负载容量仍需专项验证。上表没有测两个服务端在相同负载下的吞吐量，不能用于估算公网在线人数。


### 96 个连接的混合玩法实测

在实际部署使用的 Windows x64 主机单独运行测试区服与 96 个回环客户端。测试时使用上一发行版，手动将临时区服的连接上限调至 96。每频道 6 个角色，共 16 个频道，同时执行 6 轮档案、头像、签名更新和位置同步。

| 核验项 | 结果 |
| --- | --- |
| 业务请求和移动广播 | 2,304 次请求完成，3,456 条移动通知逐项核对通过 |
| 退出后读取存档 | 96 个角色的位置、频道、头像、签名和档案均符合预期 |
| 集中操作延迟 | 回环 RTT 中位数 0.865 秒，P95 为 1.36 秒，P99 为 1.76 秒 |
| 锁和内存 | 锁等待 P95 为 1.32 秒，SQLite 提交 P95 为 21.9 毫秒。含模拟客户端的进程峰值工作集为 106.2 MiB |

六轮集中操作历时 22.48 秒。公网玩家还需计入转发和网络延迟，同频道人数、玩法组合及持续时间也会影响结果。可用 [混合玩法基准](../../tools/benchmark_mixed_gameplay.py) 复测，参数为 `--clients 96 --group 6 --rounds 6`。

### 星云树和能力列表

原版登录会读取已学能力（1611）。玩家打开星云树时，会查询全树或所在场景（1631）。旧版在每次查树时重建国服成就编号集合，通过 447 个参数分别查找角色的成就。新版按同一角色的编号区间读取，使用国服白名单逐条过滤，再按原顺序返回。能力列表先读已学记录，只在存档确实缺少能力行、且背包持有对应道具时补写。角色等级、已领状态和库存仍随请求读取。

以下为开发机 Windows x64、i9-13900H、发行版 Python 3.13.9 / SQLite 3.50.4 上的回环 TCP 测量。固定 28 个角色，其中 14 个有完整能力道具，7 个部分持有，7 个空档。每个角色完成 12 轮全树、单场景树和能力查询，每次运行共 1,008 条请求。预热与登录排除在计时之外，旧版基线为 `76ef5c5`。各档三次独立运行，表中为中位数。

| 同时发请求的客户端 | 旧版 → 新版吞吐（请求/秒） | 旧版 → 新版 P95 往返（毫秒） |
| ---: | ---: | ---: |
| 1 | 1,081 → 1,915 | 1.78 → 0.80 |
| 7 | 1,301 → 1,835 | 6.87 → 5.05 |
| 28 | 1,341 → 1,893 | 22.42 → 16.65 |

同一完整角色完成上述三条查询，SQL 从 18 次读取、79 次插入尝试和一次事务提交降到 17 次读取。SQLite 查询计划沿用 `(player_id, achieve_id)` 的复合索引，按成就编号等值查找变为一次上下界扫描。18 次运行的完整回包摘要一致，持久化的能力和成就行摘要也一致。28 并发下，结束时整个测试进程的工作集中位数为 96.1 → 96.2 MiB，包含客户端。此次收益主要体现在延迟和吞吐。

### 28 核主机的并发边界

部署主机记录为双路 Xeon E5-2680 v4，共 28 个物理核、56 个硬件线程。原生 TCP 每个连接独立收发，游戏处理仍共享一个进程锁和一个 SQLite 主写连接。联网、发包和独立服务可并行工作，同一区服的玩法事务依次提交。上表中的 28 是并发客户端数；部署主机实测见上一节「96 个连接的混合玩法实测」。

跨多个进程承载同一世界，还需解决角色会话唯一性、跨进程频道广播、扣款与发奖的事务归属。目前各区服可用独立状态目录和端口分别部署；它们拥有各自的角色数据和在线世界。单区服扩容量时，应在同一台机器的隔离数据库同时测同频道广播、混合写入、锁等待与提交 P95，并回读存档。仅调整线程数量或增加 PostgreSQL 报表副本，不能据此提高玩家上限。

### 1、2、4 个独立区服

同一开发机固定 48 个角色、每频道 6 人，分别均匀分配到 1、2、4 个游戏进程。每个进程使用独立的 SQLite 文件和回环端口，数据库逐个确认启用 WAL 和 `synchronous=FULL`。角色完成 32 轮档案、头像、签名及位置更新。所有客户端连接和进图后同时起跑，总吞吐按最早起跑到最晚收完回复计时。三种布局的六种先后顺序各测一遍。

| 区服进程 | 每服角色 | 总吞吐中位数［范围］，请求/秒 | 混合请求 P95 中位数［范围］，毫秒 | 进程私有内存合计中位数，MiB |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 48 | 1,283［370–2,457］ | 81.9［22.5–151.7］ | 93.3 |
| 2 | 24 | 4,287［442–4,567］ | 13.8［12.2–128.7］ | 175.3 |
| 4 | 12 | 6,929［738–7,317］ | 8.4［7.7–86.5］ | 338.9 |

每次均核对 6,144 个请求、9,216 次移动投递、48 份退出后重开的角色存档。不同区服使用相同频道号，每个角色的移动坐标可单独识别；每名接收者只收到本区服、同频道的记录。18 次测量的回执、投递和存档联合摘要一致。每次记录到 4,610–4,637 次持久化事务提交，包含位置落盘。内存为业务请求结束时各进程的私有字节数，包含各自的模拟客户端。

写盘延迟在各轮间波动。同为 1 个区服，提交 P95 低于 1 毫秒的 3 次中，吞吐中位数为 2,405 请求/秒；其余 3 次为 376。2、4 个区服在该低延迟条件下的中位数分别为 4,499（4 次）和 7,180（5 次）。这组测量支持将相互独立的玩家群分配到多个区服。4 个区服的内存支出增加约 246 MiB。共用世界仍需单独验证跨进程玩法一致性，部署主机的机械硬盘也需按实际写盘延迟评估容量。

python tools/benchmark_realm_processes.py --server OverField-Server --players 48 --group 6 --rounds 32 --realms 1 2 4
