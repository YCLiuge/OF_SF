# 单区服性能审查

基线为服务端 `ad981c6`。以下为 Windows x64 同机测试。查询耗时不含公网延迟，坐标耗时只计持久化路径。

| 实测工作量 | 基线 → 当前 | 验证内容 |
| --- | --- | --- |
| 5 万角色，30 次混合昵称查询 | 好友查找 P50 134.19 → 0.0068 ms；注册查重 57.47 → 0.0314 ms | 已有名字和未命中查询均使用索引。保留注册、改名和旧档各自的比较规则。首次建索引 318 ms，数据库多占 8.06 MiB，批量改名平均每次多约 16 µs。 |
| 64 MiB 版本包，连续 20 次管理查询 | 交给 SHA-256 的包内容 1,280 → 64 MiB；P95 52.02 → 3.97 ms | 5 轮中位数。接着进行 64 次管理与公开混合并发查询，成功数 40 → 64；文件撤回、替换或损坏均复测。 |
| 24 名角色，57,600 次移动 | 存档向量编码 115,200 → 3,840 次；持久化用时中位数 113.56 → 74.75 ms | 两版均写入 1,920 行。另测两频道的 320 次移动、640 次投递，角色位置与广播一致；写入失败可重试。 |

从仓库根目录使用 [昵称基准](../../tools/benchmark_nickname_lookup.py)、[发布查询基准](../../tools/benchmark_release_queries.py) 和[坐标基准](../../tools/benchmark_pose_checkpoints.py)。用 `--help` 查看数据规模、服务端路径与轮数。发布查询使用相同测试工具分别量旧版和新版，读量统计在应用层。

### 旧档与外键

旧版成就表曾将成就编号同时指向玩家编号。本版首次打开旧库时，在同一事务内重建成就表，只保留其所属玩家关系。保留原有成就内容、行号、索引和触发器；异常会回滚。游戏主写连接启用 SQLite 外键检查。迁移遇到原有孤儿记录会保留，可在离线备份副本上运行 `PRAGMA foreign_key_check;` 检查。本机和公网的备份副本分别含 11,882 和 225,758 条成就。两次演练均逐条核对摘要，迁移后外键检查均无异常。

### 架构取舍

社区项目按频道维护成员，使用有界发送队列，并固定 Lolo 服务端与资源版本。OF_SF 已有频道索引和有界发送队列。本次根据本服回归保留广播语义，优化了存档时的编码。原版 Unity 客户端继续适用，道具、扣费和领奖仍在玩法事务内提交。[社区频道实现](https://github.com/jianx14/overfiled-mod/blob/cfdb9ed0b924f49f5f6d91f7dc23dbadfbc35ce5/%E6%9C%8D%E5%8A%A1%E5%99%A8/Chat.Server/ChannelRoom.cs) · [社区部署说明](https://github.com/jianx14/overfiled-mod/blob/cfdb9ed0b924f49f5f6d91f7dc23dbadfbc35ce5/private-server/SETUP.md)

本轮保留 SQLite WAL 单服写入和 PostgreSQL 报表副本。现有测量支持优化锁内工作量，跨库崩溃对账、高密度同场广播与持续负载容量仍需专项验证。上表没有测两个服务端在相同负载下的吞吐量，不能用于估算公网在线人数。
